## 1. 数电票 XML 解析（DeepSeek 意见 → 决策）

| 意见 | 决策 |
|---|---|
| 命名空间：ET 标签为 `{uri}tag`，别硬编码前缀；用 localname 匹配，兼容厂商差异 | **采纳**：解析器统一用 `tag.rsplit('}',1)[-1]` 取 localname |
| 专/普票字段层级不同 → 立即映射统一 `Invoice` dataclass，规则层不碰 XML 树 | **采纳**：models.Invoice 为唯一中间契约 |
| 金额用 `Decimal(str)` 禁 float；勾稽 `金额+税额==价税合计` 容差 ±0.01，不平时记"勾稽异常"不抛错 | **采纳**：Decimal 全链路；勾稽异常作为 Finding 而非中断 |
| 税额可能为 `*` 或空；日期 `yyyyMMdd` 转 ISO | **采纳**：空值→解析告警；日期统一 ISO |
| 多税率明细行、折扣行、红票负数按行汇总 | **采纳**：明细行聚合逻辑 |
| `iterparse` 读 bytes 规避编码声明不符 | **采纳** |
| 字段缺失降级为解析告警，不中断整批 | **采纳**：parse_warnings 进契约 |

## 2. 规则引擎服务化（DeepSeek 意见 → 决策）

| 意见 | 决策 |
|---|---|
| 契约：解析层输出 `NormalizedInvoice`（Pydantic，含 batch_id/source_hash/parse_warnings）；规则引擎只依赖该模型+ruleset_version；输出 `Finding(rule_id, severity, confidence, invoice_no, field, message, evidence)` | **采纳**：models.py 定义契约 |
| 接口拆 `POST /parse` 与 `POST /review`，可独立测试替换 | **采纳** |
| R1/R3/R6 是跨票规则，必须整批一次入参（逐张调用会让重复/连号失效） | **采纳**：/review 为批量接口 |
| 单批上限 500 张，超限分片但共用 batch_id 做全局去重 | **采纳**：分片共享 batch_id |
| 性能：纯内存 O(n log n)；asyncio.to_thread 包 CPU 段；回传 ruleset_version 与耗时 | **采纳** |

## 3. 风险报告信息架构（DeepSeek 意见 → 决策）

自上而下：①汇总条（票数/金额合计/通过/待复核/拦截数）②风险清单（严重度降序：规则名/票号/命中字段/原始证据/建议动作）③发票明细表（关键字段+状态标签，可定位风险）④规则版本与验证范围 ⑤免责。

- 分级用**双标签**：严重度（高/中/低，看财务后果）与置信度（确定/疑似，看证据强度）分离；
- R1/R2/R7 多为高严重高置信；R6 偏低置信标"建议关注"；
- 免责文案（固定每屏页脚，导出保留）："基于 XML 结构化数据的规则预审，不替代人工复核与税务判断；命中项需核原始凭证，未命中不等于合规；规则版本与覆盖范围已列明"。

## 4. P1 范围批判（DeepSeek 预警 → 决策）

| 预警 | 决策 |
|---|---|
| OFD 是 ZIP+多层 XML+版式+SM2/SM3 签章验签，难度高一个量级；P1 别上半个解析器 | **采纳**：P1 只做输入类型识别，OFD 明确"暂不支持"并给出提示 |
| 用户实际常传打印 PDF/截图 → 用 magic bytes 前置探测（%PDF / PK / <?xml），按类型给明确路由提示 | **采纳**：上传入口做类型探测，"不支持的输入类型"作为 P1 一级能力 |
| 同批专普混合/红蓝混合/跨月跨年 → 阈值按票种分组 | **采纳**：规则按票种分组 |
| 旧版与不同开票平台的 ns/字段别名差异 → 建别名映射表 | **采纳**：parser 内置别名映射 |
| zip 内多张票/超大文件/同一票重复上传 | **采纳**：上传限制与去重（source_hash） |
| 金额落在图片里字段为空 → 绝不默认 0 | **采纳**：空值→解析告警 |
